Brief to Reliable Agent Validation Engine

How BRAVE turns one written brief and one tool API file into a tested Freya phone agent for debt collection: every stage, every rule and the reasons behind them.

30 minbudget for the whole build
≤ 2model calls at build time (extract, repair)
0bank values written by the model
10/10 · 3/3Brief A · Brief B, every customer 3 of 3 runs

01The task

Build the builder: a program that reads a brief it has never seen and publishes a working phone agent on the Freya platform, without a human in the loop.

Input

  • Brief (markdown): the bank's collections policy. Opening lines, identity questions, days-late bands, deadlines, holidays, floor amounts, persuasion attempts, the outcome table. Brief A has 47 numbered rules. A final brief may be raw material instead (mail, memo, code list).
  • Tool API (OpenAPI JSON): verify_identity, get_account, create_promise, add_note, schedule_callback, transfer_to_agent, close_call. Field names and enums can change from brief to brief.

Output and scoring

  • A published Freya workflow (the agent), its export, and a trace of the build.
  • Simulated customers call the agent. A call passes only if all three hold: the bank ledger shows the right outcome (promises, notes, callbacks, transfers, close reason), the policy was kept, and the agent was honest.
  • No partial credit. A customer counts only if 3 of 3 runs pass, on different calendar days.
What this means for the design: consistency matters more than eloquence. One wrong amount, one promise recorded without a clear yes, or one date off by a holiday fails the customer. The builder has to be right about numbers every time.

02Core principle: a deterministic skeleton around the model

The model understands language. Code makes every decision that touches the bank.

modelWhat the model does

  • At build time: reads the brief once and fills a fixed JSON spec (one call, one repair call at most).
  • At call time: speaks the lines it is given, classifies each customer reply into an enum (yes, offer, hardship …), copies date and amount words exactly as said, answers a side question in one sentence.
  • Fills only the two verify_identity arguments, and a pre-hook normalises them.

codeWhat code does

  • Builds the whole workflow from a template. Same spec in, same workflow out.
  • Decides offers, amounts, dates, which product, when to record, transfer or close.
  • Parses spoken dates, times, amounts and birth dates against the call's own clock.
  • Every value sent to the bank comes from a code node or is baked into the request.

Why not let an agent write the workflow?

  • A model-written workflow varies from run to run. Here the score requires 3 of 3.
  • There are no practice customers for a hidden brief, so a build cannot test its way to correctness.
  • 30 minutes fits one or two simulated calls, not an optimisation loop.
  • The agent model on the platform is weak at arithmetic and dates. Code is not.

04Reading the tool API

Nothing about the bank's tools is assumed. Names, fields, required flags and enums all come from the OpenAPI file.

Tool definitions

  • Base URL from servers[0]. Tool name from operationId, else the last path segment.
  • Request body $refs resolved. Each property becomes a field: type, description, enum, required, format, default.
  • Response view: the 200 JSON schema is followed through $ref, allOf, oneOf, anyOf (depth cap 20). Example: create_promise 200 written as allOf[$ref Error, {promise_id}] still lists promise_id.
  • Fixed values: a field's default, or the only value of a one-value enum, is baked in.

How success is read

  • An ok flag, if the response has one.
  • Else the first field that is not an error or message (e.g. promise_id present).
  • Else "no error field".
  • A flag is only wired if the response really has it. Wiring a flag that never arrives would read every call as failed.
  • Baked fields are sent as {{var}}: the model never sees or fills them.

05Spec extraction

One model call turns the brief into a fixed JSON schema. Temperature 0, OpenRouter, model set by BUILDER_MODEL_BUILDER.

What the prompt contains

  1. Role and precedence: later or overriding sources win, judged against the call's now. Every such decision is written to notes.
  2. Hard rules: never invent; every code comes from the tool API's enums; state every product, then handle them one at a time (up to 3).
  3. Policy help: what each policy knob means and which values it takes; what each spoken line is for.
  4. Tool summary: per tool, method, URL, fields with type / required / enum / description, and the resolved response.
  5. The schema, then the brief between <<< and >>>.

06Checks and the repair round

The model's spec is checked by code against the tool API and against the brief's own text.

check()

  • Every close, note, queue and identity value is in the tool's enum
  • Holidays are ISO dates; bands are integers; all 11 knobs present
  • tool_fields name real fields
  • Required lines present; no {{ except in who_question

bindings() · responses()

  • Every required request field has a role or a fixed value
  • Response fields the workflow reads really exist (ok, verified, wrong_answers_left, hint, product list path)
  • Every product type has a floor field and a spoken name
  • Close reasons fit close_call's enum

structure()

  • Bands do not overlap or leave gaps (next min = previous max + 1)
  • Callback times are HH:MM with start < end
  • attempt_plan is at least as long as the longest band's attempts
  • Reason priority maps to known reasons

Grounding: is it really in the brief?

A heuristic check that the values that move the score appear in the brief's text: holiday dates (in any written form), band numbers (digits or words), callback times (24 h or am/pm), every outcome and reason code as a whole token, and a callback rule that says "business day".

  1. Repair round, only if a check failed: the same conversation continues with "These checks failed: …". The model fixes them from the brief and the API. A value "not found in the brief" may stay only if the brief says it, with a note quoting where. The whole JSON is returned again. There is no second repair.
  2. Deterministic overrides: e.g. if a callback sentence names "business day" and no weekend, callbacks are forced onto business days (a real extraction once offered a Saturday).
  3. Blocking: only two problems stop the build: no identity question, or no usable band. Everything else is logged and the build continues.
An imperfect agent beats no agent. One false positive in a check once ended a run with nothing published. Now open problems are logged (ok_spec_problems) and the agent is still built, validated and published.

07From spec to engine config

  • Defaults fill missing knobs: workdays Mon–Fri, callback 10:00–19:00, 1 business day ahead, DMY dates, attempt 1 on the last business day of the week.
  • Neutral lines: every line the engine can say gets the brief's wording or a neutral sentence (24 keys). A hidden brief never inherits Brief A's wording such as "You will receive a text message" or "You can change it in the mobile app".
  • Bank codes mapped back: a reason priority written as bank codes is mapped to the engine's semantic keys (refused, hardship, dispute, service_error).
  • Attempts capped at the length of the attempt plan, so the agent never repeats an offer the customer already refused.

08The generated call flow

A deterministic template. Four node kinds: conversation code api_request end_call, plus one lifecycle close_call that always runs at the end of the call.

Phases of a call

  1. Opening (conversation, cap 3 then opening2): who1 ∈ confirms, someone_else, wrong_number, deceased, wants_human, question, unclear. The first node is a conversation because a code node as first node never runs on the platform.
  2. Identity: setup_id computes calendar facts, then identity holds verify_identity. Turn cap 60. A refusal goes through decline_check to identity2 before closing as declined.
  3. Account: get_account maps the product list; facts builds per-product facts. The facts the model sees leave out the floor and the deadline, so it cannot make offers on its own.
  4. Negotiation loop: negotiate_say speaks the engine's line; after each customer turn decide runs the engine and routes on neg_action: say, record, transfer, finish, or answer a question (negotiate).
  5. Recording: record calls create_promise with values from code; after_record reads the result and routes like decide.
  6. Wrap: wrap → note (loops once per product that needs a note) → goodbye.
  7. Third party: someone else answers → ask for a callback time, check it in code (cb_check), book it with schedule_callback.

What the model extracts on each negotiation turn

reply_kind: yes · no · offer · too_much · vague · paid · dispute · hardship · restructure · human · stop · question · evasive · unclear said_date_textsaid_amount_textall_productshas_questionabout_product: p1 · p2 · p3 · none

Date and amount are copied as words. The engine parses them; the model never computes them.

Writes to the bank

  • Write tools get a 25 s timeout (a slow add_note once arrived after close_call).
  • No automatic retry on writes, to avoid double promises. get_account retries once, close_call twice.
  • "Already recorded" or a bare 409 counts as success.
  • The close_call pre-hook: if the customer hung up with no outcome, it rebuilds one from the engine state (recorded promise → promise; all paid → paid; negotiating → no_promise with the right reason; never verified → not_reached).

09Identity verification

Pre-hook (before verify_identity)

  • Date answers go through normalize_dob. A lone century ("19", "198") is sent as incomplete, so the bank does not count it as a wrong answer.
  • Digit answers go through digits_from_speech ("double four seven one" → 4471). If the model joined pieces in the wrong order, the heard order wins.
  • The heard words (id_heard, id_last) are used once, then cleared.

Post-hook (after)

  • Writes one instruction for the model: year incomplete · day/month swapped hint · both correct · unreadable · locked · "Correct. Now ask: …" · wrong.
  • Verified when the bank says all_verified, or, when the API has no such flag, when the hook counts every question answered right (id_all_ok).
  • wrong_answers_left = 0 → failed. A second 5xx → service error close.
Gate: get_account, create_promise and add_note are unreachable in the graph until the verified transition. The validator proves this before saving, and the smoke test fails if the agent says "debt", "overdue" or any forbidden word before verification.

10The negotiation engine

negotiation_lib.py runs inside code nodes. Every customer turn: read the reply, take one step, publish the next line and action.

State per product

fullfloor ≤ fulldeadlinedays_lateattemptsusedrefused_offersamountdate

status: open → agreed → recorded, or refused · hardship · paid · dispute · failed

Global state

phase: ask_today · offer · confirm · recording · closing · hardship_offercurrent producthuman_askedstopnoteslast_askunclear_run

Opening the negotiation

"Your card has £X past due and is D days late." for each product, then "Can you make this payment today?" or, with several products, "Can you pay all of them today?". A no to the combined question goes on with "Let us go through them one at a time." so it is not counted as attempt one on every product.

Reading a reply

  • Date and amount words are parsed by code. "The minimum" / "all of it" map to floor / full. Unreadable number words → "Sorry, how much can you pay?" (twice, then evasive).
  • A yes, no or too_much that carries a date or an amount becomes an offer: a date the customer names is never a refusal.
  • The raw last message is read from the conversation. "Both" / "all of them" means every product, unless the same message refuses.
  • Cut-off turns (no end mark): a cut stop / no / evasive without a value becomes unclear, so it uses no attempt. The third cut turn in a row is taken as said.

One step: the decision order

  1. Join an amount said in two pieces ("Sorry, I think you were cut off. Please go on.").
  2. Pick the product: the one named, else the current one. An offer for a refused product reopens it.
  3. Price-style re-read: "three fifty" is read as 350 when 3.50 is outside [floor, full].
  4. "Yes, that Tuesday" to an offered Tuesday keeps the offered date.
  5. Restructure → transfer. Person requests: help first, transfer at human_requests_to_transfer.
  6. Hardship → by policy: offer support (sympathy once, offer once), transfer, or close. No persuasion after hardship.
  7. Stop: counted; at stop_requests_to_close open products are refused and the call ends.
  8. Paid / dispute: set on the named product, move on.
  9. Question → the model answers in one sentence, then repeats the last ask exactly.
  10. Confirm phase: a yes is checked again (floor ≤ amount ≤ full, date rules). Only then action = record. A no asks which promise to change; a new offer reopens it.
  11. Offer phase: yes accepts the offer on the table; no / evasive → next attempt; an offer is applied; too_much → the floor on a valid day, once.

Attempts and offers

Attempt plan (Brief A)

  • Attempt 1: the current amount (the floor if the customer said too much) on the attempt-1 date, the last business day of this week.
  • Attempt 2: the floor on the deadline.
  • Dates are clipped to the deadline. A refused (amount, date) pair is never offered again. "The rest stays overdue." when below full.
  • When all attempts are used, the product is refused.

Applying a customer offer

  • Amount capped at full. Below floor: "I cannot record X. The minimum is F. Could you pay F on D?"
  • No day → "On which day can you pay X?". Vague day → "On which exact day?", then "The latest date I can record is …".
  • Date check: ok · past · after deadline · not a business day → the next business day is offered.
  • With several products each keeps its own deadline.

Recording and closing

  1. When nothing is open: read-back "To confirm: £X on Friday 23 October for your card; … Do you confirm?"
  2. Only a yes to the read-back records. One create_promise per agreed product, values from code, up to promise_attempts tries; a failure continues or transfers by policy.
  3. A recorded promise is never undone. A transfer drops agreed but unrecorded promises.
  4. Finish: one note per product not recorded (when the brief uses notes); outcome = transferred · promise · paid · no_promise. The no_promise reason is the first product's status, or the first of reason_priority [dispute, hardship, service_error, refused].
Record only what the customer confirmed, inside the rules. This single rule removes the most expensive failure: a promise in the ledger that the customer never agreed to.

11Speech parsing

Phone speech is messy: number words, self-corrections, cut-off sentences. speech_lib.py reads it relative to the call's now, because the platform's extractor anchors dates to the real clock.

  • Self-corrections: split on "sorry", "I mean", "no wait", "actually", "make it", or a bare "no" after punctuation; keep the last part that holds a value.
  • Number words: "twenty-second" → 22nd, "four hundred and fifty-five" → 455; "thirty seven fifty" starts a new number.
  • Unsure means ask again: two separate numbers, a percentage, a range or an unreadable year return nothing, and the agent asks again. It never guesses.

12Calendar rules

Business days

  • A business day is a workday that is not a holiday (both from the spec).
  • Deadline: the Nth business day after today, or N calendar days moved back to a business day.
  • Attempt-1 date: last business day of this week, or of next week if today is already that day.

Bands (Brief A)

  • early 1–7 days late: deadline 12 business days, 1 attempt.
  • late 8–45 days late: deadline 7 business days, 2 attempts.
  • Holiday 26 Oct 2026 is skipped in every count. A 28-day date table is computed once per call.

13Fitting code into code nodes

The platform's code_exec takes 131,072 bytes of code plus call data, and the data grows by about 1.3 KB per customer turn. A call failed at turn 51 with 66 KB of code.

  1. AST subset: each node gets only the library functions, constants and imports its body actually reaches.
  2. Snippet = header, library subset, CFG = json.loads(…) with the engine config, then the body in try/except that sets code_error.
  3. Over 30 KB, the library is stripped of docstrings and packed with zlib + base64, then unpacked into globals(). The largest node drops from 36 KB to under 28 KB.
  4. No {{ or }} anywhere: the platform would read it as a template placeholder.

14The validator

Runs before anything is sent to Freya. An error stops the run; the exported file is checked again after save.

Integrity and shape

  • Initial node exists; node names match keys
  • Tools only on conversation nodes; pre-actions only on api/code nodes
  • Passthrough nodes end with an always transition
  • end_call nodes have no transitions

Conditions and turns

  • Every conversation node has a turn cap that does not point to itself
  • Deterministic operators only; numeric operands for gt/lt
  • No dead transitions after an always
  • Extraction confidence and prompts checked

Code safety

  • Syntax; size (error over 71 KB, warning over 36 KB)
  • No network, process or __import__; no eval of call data
  • Packed blobs unpacked and scanned too

Scope

  • URL, host and method match the OpenAPI file
  • Required fields present; enum values valid
  • No unknown parameters

Graph

  • Every node reachable
  • Every node has a path to an end
  • No passthrough cycles except bounded loops

Policy

  • Gated tools unreachable before verification
  • create_promise only in record
  • Exactly one lifecycle close_call at end of call
  • No debt variables exposed before verification

15Deploy and run

  1. Dry run (dryRun=true). A 4xx means the platform read the workflow and refused it: write the local file and stop. Any other failure is ignored, because saving validates again.
  2. Save and publish into one slot per brief: create on the first run, update and publish the newest version afterwards.
  3. Smoke test (if more than 60 s are left): one "Hello?" over the chat API with sample variables. It fails on an error, or if the reply says "debt", "collections", "past due", "overdue" or a forbidden word before verification.
  4. Export from the platform; if that fails, the workflow as sent is written instead. A submission file always exists once a workflow is saved.

Budget and retries

  • 30 minutes in total; 3 kept for save and export; 60 s for the smoke test.
  • Freya calls: at most 120 s each, cut to the time left. 5xx, 429 and dropped connections are retried with backoff 4 → 30 s; a 4xx is an answer.
  • Model calls: 300 s each, retried, never started with less than 20 s left.
  • A previous run's trace and export move to runs/<brief>/<time>/, never overwritten.

The trace's END line

  • ok: published and the smoke test passed.
  • ok_spec_problems: published with logged spec problems.
  • Suffixes: _smoke_failed, _smoke_skipped, _export_failed.
  • Stops: spec invalid, generation failed, invalid workflow, dry run refused.
  • Every model call is logged with tokens and cost; keys are redacted.

18Results and tests

Public practice set (13 customers)

  • Model-extracted spec, full build: Brief A 10/10, Brief B 3/3, every customer 3 of 3 runs.
  • Hand-written spec, same generator: the same result.
  • Talkative style, after the fixes: Brief B 3/3 on all three runs; Brief A 10/10, 9/10 and 5/10 (the 5/10 on a slow-model run).
  • Spec extraction: about 50 s and $0.15 per build.

Tests

  • tests/hack: 25 files, 355 test functions (more when parametrised). Engine, policy, invariants, speech, calendar, generator, validator, spec checks, regressions from reviews.
  • Local harness: the real code-node snippets run against a mock bank (3-wrong-answer lock, swap hint, injected faults) and are scored with the organisers' scorer.
  • Unseen-brief sample (tests/metamorphic/northwind) checks that nothing is tied to Brief A.

The ideas in one list

  1. Language to the model, numbers to code. The model talks and classifies; code decides and writes.
  2. Everything from the inputs. Field names, enums, bands, lines and policy come from this brief and this API.
  3. Check the model against the source. Enum checks against the API, grounding against the brief, one repair round.
  4. Prove the gates before publishing. The validator shows no account data or bank write is reachable before identity is verified.
  5. Ask, never guess. An unreadable date, amount or year is asked again.
  6. Ship something. A logged, imperfect agent scores more than none.
